# imgcache Web Delivery Plan v1

Goal: make imgcache derivatives consumable from a SvelteKit application (SSR + browser)
without weakening the ground setup. The ZMQ worker remains the only cache writer and the
only key authority. No QUIC/HTTP code is added to Python.

## Architecture overview

```text
CONTROL PLANE (small messages, trusted network)
  SvelteKit server (Node) ──zeromq.js REQ/REP──▶ imgcache ZMQ worker
      sends: spec payload (JSON)            returns: relpath (cache hit guaranteed after)

DATA PLANE (image bytes, public)
  Browser ──HTTPS (h3 via Alt-Svc)──▶ Caddy ──sendfile──▶ shared volume (read-only)
      URL: /cache/leaves/<xx>/<key>.<ext>?exp=...&sig=...
```

Design rules (do not violate):

1. Worker is the only writer under `cache/`. Caddy mounts the volume **read-only**.
2. Key derivation exists **only in Python**. The TypeScript client never hashes,
   never canonicalizes params, never builds paths. It sends specs and receives relpaths.
3. Only `cache/leaves/` (signed URLs) and `cache/pinned/` (explicitly published, public) are
   web-exposed. `raw/` and `cache/nodes/` are never served.
4. Browsers can only fetch URLs already resolved by the SvelteKit server. Caddy never
   triggers renders (no render-amplification surface on the public plane).
5. Image URLs are minted in exactly one place (SvelteKit server) and HMAC-signed there.

## Existing wire contract (reference, already implemented)

Transport: ZMQ REQ/REP, JSON messages. Client behavior to replicate from
`src/imgcache/zmq_client.py`: request retries, timeout, and transparent handling of the
worker busy/retry protocol (inspect `zmq_worker.py` for the busy response shape).

Requests:

```json
{"method": "materialize", "spec": { ...spec payload... }}
{"method": "identify",    "spec": { ...spec payload... }}
{"method": "health"}
```

Responses:

```json
{"ok": true, "relpath": "cache/leaves/e7/<key>.webp"}
{"ok": true, "meta": { "width": ..., "height": ..., "n_pages": ..., ... }}
{"ok": false, "error": {"type": "...", "message": "..."}}
```

Spec payload shape: produced by `ImageSpec.to_payload()` (see `SourceSpec.to_payload`,
`Operation.to_payload`, `EncodeSpec.to_payload` in `src/imgcache/spec.py`).
The TS client mirrors this **payload shape only** — treat it as the wire schema.

## Milestone 1 — Wire schema freeze (Python, ~0.5 day)

Deliverables:

- `docs/wire_schema.md`: document the exact JSON payload produced by `to_payload()`
  for source, each operation (`page`, `normalize`, `scale`, `resize`, `crop`,
  `crop_fraction`, `rotate`, `fast_rotate`, `flip`, `flop`) and each encode
  (`webp`, `png`, `jpg`, `avif`, `tif`), including required/optional fields and types.
- `tests/golden/specs.jsonl`: golden fixtures generated by a small Python script —
  each line contains `{ "spec": <payload>, "relpath": "<expected leaf relpath>" }`
  for ~20 representative chains (image + PDF, all ops, all encodes, param edge cases:
  floats, defaults omitted vs explicit, operation order variations).
- Python test asserting the fixtures stay valid (guards against accidental wire drift;
  bump `engine_version` when intentional).
- `tests/golden/hashes.json`: byte-sequence -> xxh3-128 hex vectors (a handful: empty,
  small ascii, binary, multi-MB) consumed by both Python and TS test suites to validate
  the ingest hasher (`xxhash-wasm` vs Python `xxhash`).

Acceptance: `uv run pytest tests/test_wire_schema.py` passes; fixtures are committed.

## Milestone 2 — TypeScript client package (`@imgcache/client`, ~2 days)

New repo directory `clients/typescript/` (own `package.json`, publishable).
Dependencies: `zeromq` (zeromq.js ^6). Dev: `vitest`, `typescript`.

API (server-side only — this package must never be bundled for the browser):

```ts
import { ImgCache } from "@imgcache/client";

const cache = new ImgCache({ endpoint: "tcp://127.0.0.1:5555", timeoutMs: 300_000, retries: 2 });

const spec = cache.open(fileId, "application/pdf").page(1, { dpi: 144 }).scale({ longestEdge: 1024 }).webp({ quality: 82 });
const { relpath, key } = await spec.resolve();   // ZMQ materialize
const meta = await spec.identify();               // ZMQ identify -> { width, height, nPages, ... }
const ok = await cache.health();
```

Implementation notes:

- Builder objects are immutable; each op returns a new instance (mirror Python semantics).
- `resolve()` sends `{method:"materialize", spec}` and returns the worker's relpath verbatim.
- Replicate retry/busy handling from `zmq_client.py` (REQ socket recreation on timeout,
  bounded retries, busy-response backoff). Use one lazily-created socket per instance;
  serialize requests through a promise queue (REQ/REP requires strict alternation) or use
  a small socket pool (size configurable, default 4) for concurrency.
- In-process memoization: `Map<payloadJson, relpath>` with LRU cap (default 10k entries).
  Safe because leaves are immutable; eviction of the file is handled by re-resolving on
  demand only if serving fails (see Milestone 4 note on 404 handling).
- Ingest helper: `cache.ingest(buffer | path, mime)` — see Open Decision 1. Note: in the
  current design clients already own `raw/` ingestion (`OriginalsStore.put`), and
  `file_id` is a plain xxh3-128 over file bytes (no canonicalization involved), so a
  TS-side implementation validated by shared golden hash vectors is much lower-risk than
  spec-key porting would be. Must replicate the atomic write pattern (tempfile in `raw/`,
  then rename).

Tests (vitest):

- Golden test: for every line in `tests/golden/specs.jsonl`, build the same chain with the
  TS builder and assert the serialized payload deep-equals the fixture payload.
- Integration test (CI job with a real worker container): resolve fixtures against the
  worker from `Containerfile.worker`, assert returned relpaths match fixtures and files exist.

Acceptance: golden payload parity 100%; integration test green against the container.

## Milestone 3 — URL signing (Node + verifier, ~1 day)

Signed URL format (query-string style, path untouched so Caddy file matching still works):

```text
/cache/leaves/e7/<key>.webp?exp=<unix_ts>&sig=<hex hmac-sha256(secret, path + "\n" + exp)>
```

Deliverables:

- `@imgcache/client` export: `signUrl(relpath, { secret, ttlSeconds })` and
  `publicUrl(relpath, opts)` returning the full `https://images.../...` URL.
- Verifier: a `+server.ts` route in the existing SvelteKit app (`/api/imgcache/verify`)
  used as the Caddy `forward_auth` target: checks `sig` and `exp` from `X-Forwarded-Uri`,
  returns 204 or 403. Constant-time compare (`crypto.timingSafeEqual`). Secret from env
  `IMGCACHE_URL_SIGNING_SECRET` (32+ random bytes). No extra service needed.
- Alternatives documented: standalone micro-service (only if the app ever moves off Node),
  or a custom Caddy build (xcaddy) with a community signed-URL module (avoid: pins you to
  custom Caddy binaries).

Rules:

- Default signed TTL 1h. Expired links: 403 (browser cache still serves already-fetched
  images within its `immutable` window — acceptable and intended).
- Public tier: `publishUrl(spec)` materializes with `MaterializePolicy.PIN` (leaf lands in
  `cache/pinned/`, excluded from TTL eviction — required, since default eviction TTL is
  7 days) and returns an unsigned URL under `/cache/pinned/...`. Same
  `Cache-Control: public, max-age=31536000, immutable` header as signed leaves — URLs are
  content-addressed and never change meaning, so one header rule covers both tiers.
  Publishing is an explicit server-side act; unpublish = unpin + stop emitting the URL
  (already-fetched copies may persist in browser caches until evicted there).
- Signature covers path + expiry only (not query extras), so future params don't break sigs.
- Key rotation: support `IMGCACHE_URL_SIGNING_SECRET_PREVIOUS` accepted during overlap.

Acceptance: unit tests for sign/verify round-trip, tamper (path, exp, sig), expiry, rotation.

## Milestone 4 — Caddy data plane (~0.5 day)

`deploy/Caddyfile`:

```caddyfile
images.example.com {
    root * /shared/imgcache

    @leaves path /cache/leaves/*
    forward_auth @leaves sveltekit:3000 {
        uri /api/imgcache/verify
        copy_headers X-Forwarded-Uri
    }
    header @leaves Cache-Control "public, max-age=31536000, immutable"
    file_server @leaves

    @public path /cache/pinned/*
    header @public Cache-Control "public, max-age=31536000, immutable"
    file_server @public

    respond 404   # everything else: raw/, nodes/, directory listings
}
```

Notes:

- Caddy serves HTTP/3 by default when given a TLS-enabled site — no extra config. Verify
  `Alt-Svc: h3` header is present and browsers upgrade (chrome://net-internals or devtools
  Protocol column).
- Mount the volume read-only in the Caddy container (`:ro,Z`).
- 404 handling: a signed URL can 404 if TTL eviction removed the leaf after resolve.
  The SvelteKit server resolves per page render, so the window is one page lifetime —
  acceptable. If it becomes an issue, lower page cache times or have the image `onerror`
  handler re-request the page data. Do **not** let Caddy trigger renders.
- Extend `examples/compose.yaml`: add `caddy` + `verifier` services, shared volume `ro`,
  worker unchanged, healthchecks for all three.

Acceptance: compose stack serves a signed leaf URL over h2 and h3; unsigned/tampered/
expired leaf requests get 403; pinned files serve unsigned with the immutable header;
`/raw/*` and `/cache/nodes/*` get 404.

## Milestone 5 — SvelteKit integration reference (~1 day)

Deliverable: `examples/sveltekit/` minimal app demonstrating the intended usage pattern.

- `src/lib/server/imgcache.ts`: singleton `ImgCache` instance (server-only module —
  SvelteKit enforces this via `$lib/server`), plus `imageUrl(spec)` helper that resolves
  and signs in one call.
- `+page.server.ts` example:

```ts
export const load = async () => {
  const doc = cache.open(fileId, "application/pdf");
  const pages = await Promise.all(
    [1, 2, 3].map(async (n) => imageUrl(doc.page(n, { dpi: 144 }).scale({ longestEdge: 1024 }).webp({ quality: 82 })))
  );
  return { pages };
};
```

- `+page.svelte` renders `<img src={url}>`; document `srcset` pattern (resolve 2–3 widths).
- Document deployment: SvelteKit Node adapter runs in the same compose network as the
  worker; `zeromq` is a native dep — pin Node version, use the official prebuilds, and
  note that serverless/edge adapters are **unsupported** (needs long-lived sockets).

Acceptance: `docker compose up` from the example serves a page whose images load over
signed URLs with immutable caching; second reload issues zero image requests (browser cache).
